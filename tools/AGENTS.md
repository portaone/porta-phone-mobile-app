# AGENTS.md - tools

`webtrit_phone_tools`, the pure Dart CLI that configures a brand's build: it fetches the build
bundle, translations and fonts from the configurator API and writes them, with generated
configs, keystores and metadata, into a phone checkout. No Flutter APIs, widgets or
`BuildContext` here. This page holds what is true for every change; what each command does and
takes is in [the commands](docs/reference/commands.md).

## Layout

```
bin/webtrit_phone_tools.dart   entry point; the only place that calls exit()
lib/src/
  command_runner.dart          WebtritPhoneToolsCommandRunner: global flags, addCommand(...)
  commands/                    one command per file or per directory
    app_resources/             configurator-resources: command, models/, services/,
                               processors/, utils/, constants/
    app_configure/             configurator-generate: command, models/, runners/
    app_setup/                 configurator-setup: command, models/, runners/
    translations_fetch/        configurator-translations-fetch
    update_command.dart        update
  configurator/                ConfiguratorClient: tested, used by no command
  utils/                       HttpClient, JSON and asset helpers
  extension/                   one extension per file
  constants.dart               configurator URL and other constants
  version.dart                 generated by build_runner
test/src/                      mirrors lib/src/; support/ holds the fake configurator backend
tool/docs_gate.dart            link and reachability check of README, AGENTS and docs/
docs/                          guides/, reference/
```

## Toolchain

- There is no SDK pin in this package. Use the Dart of the Flutter that `phone/.fvmrc` pins;
  Jenkins uses the same Flutter, installed by the `tools-test` stage of the root `Dockerfile`
  (`FLUTTER_VERSION`). The git hooks call `dart` from `PATH`, so keep that the same version.
- Two path dependencies, both in this repository: `webtrit_analysis` (`../analysis`, the lint
  rules) and `theme_schema` (`../phone/packages/theme_schema`, declared but imported by nothing
  under `lib/`). `dart pub get` needs both directories.

## Commands

```bash
dart pub get
dart format --output=none --set-exit-if-changed .   # what the commit hook checks
dart analyze
dart test
dart test --run-skipped test/ensure_build_test.dart # version.dart matches pubspec
dart run build_runner build --delete-conflicting-outputs   # regenerates version.dart
dart run tool/docs_gate.dart                       # links and reachability of the docs
dart run bin/webtrit_phone_tools.dart --help       # the CLI from source
```

Installing it and running it against a phone checkout: [running it](docs/guides/running-it.md).

## Rules for every change

Code:

- English and ASCII only in source, comments, logs, strings and keys.
- A comment says why - the rationale, the platform fact, the failure it guards against - in
  full, for a reader without our tickets. DartDoc on public API.
- 120 columns (`formatter.page_width` in `analysis_options.yaml`), single quotes, required
  named parameters before optional ones, no `.0` on a double literal that can be an int. The
  lints come from `webtrit_analysis`; `dart analyze` reports them.
- Imports in four groups, a blank line between, alphabetical inside: `dart:`, external
  packages, `package:webtrit_phone_tools/...`, relative.
- A directory with several files exports them through a barrel named after it
  (`commands.dart`, `utils.dart`, `models.dart`), one `export` per file, alphabetical.
- `dynamic` only where JSON is parsed (`Map<String, dynamic>`); typed everywhere else.
- Extensions live in `lib/src/extension/`, one per `<type>_extension.dart`, exported by
  `extension.dart`, without side effects.

Commands:

- A command extends `Command<int>` and is registered in `WebtritPhoneToolsCommandRunner`
  (`lib/src/command_runner.dart`) with `addCommand(...)`. Names are lowercase and hyphenated
  (`configurator-resources`). `description` is set, through `CommandHelpFormatter` where the
  command has a `<directory>` argument; no command sets `summary`.
- `run()` returns an `ExitCode` code (`success`, `usage`, `data`, ...), never calls `exit()`.
  It reads `argResults` inside `run()`, not in the constructor. Every `addOption` /
  `addFlag` has a `help:` string; a required input is `mandatory: true`.
- Dependencies go in through the constructor and are kept as `final` private fields. The
  runner builds and passes `Logger`, `HttpClient` and `PubUpdater`; a process runner
  (`FlutterRunner`, `FirebaseSetupRunner`) is an optional argument the command defaults
  itself, so a test can pass a fake.
- All terminal output goes through the injected `Logger` (`mason_logger`): `info`, `success`,
  `err`, `detail` for verbose output, `progress` for a long step, always ended with
  `complete` or `fail`. No `print` or `stdout.write`.
- Errors: `run()` catches `UsageException` and returns `ExitCode.usage.code`; any other
  failure is logged with `err`, its stack trace with `detail`, and returns an error code.
  Inside, catch a specific type where a step can recover or skip (`FormatException`,
  `http.ClientException`), and log what was skipped.

Structure of a multi-step command (see `app_resources/`):

- `models/` holds the immutable context built in `run()` from `argResults` (and, for
  `configurator-generate`, the session cache file) - `CommandContext`, `AppConfigureContext` -
  and the parsed API models (`BuildBundle`). Nothing changes a context after it is built.
- `services/` puts the bundle on disk (`BundleWriter`: its documents and the pictures they
  name); `processors/` handle one kind of resource each (translations, fonts, certificates,
  generator configs, local configs); `utils/` hold pure helpers; `constants/` the paths
  written into the phone checkout.
- `runners/` own process spawning: every `Process.start` / `Process.run` is in
  `FlutterRunner` or `FirebaseSetupRunner`. Binaries come from `PATH`, never an absolute path;
  check the exit code and log the output before failing.
- HTTP: every configurator call a command makes goes through `HttpClient`
  (`lib/src/utils/http_client.dart`): `getBuildBundle`, `getTranslationFiles`,
  `getCatalogTranslationFiles`. It retries a 5xx or an `http.ClientException` up to 3 times,
  after 5, 15 and 30 seconds plus up to half again as jitter, and fails at once on any other
  status. `FontAssetProcessor` downloads fonts with its own `http.Client` and retry.

Tests:

- Every command has a test under `test/src/commands/`; `test/src/` mirrors `lib/src/`, and a
  new processor, service or util with logic gets its own test. `mocktail` mocks `Logger`,
  `HttpClient`, `PubUpdater` and the runners; end-to-end runs use the loopback fake in
  `test/src/support/fake_configurator_backend.dart`, never the real backend.
- A command test registers the command on a bare `CommandRunner<int>('test', 'test')` with
  mocked constructor arguments, calls `run([...])` and asserts on the exit code and the logger.
  Only `command_runner_test.dart` and `update_command_test.dart` build
  `WebtritPhoneToolsCommandRunner`.

## Before handing over

- `dart format`, `dart analyze` and `dart test` are clean in `tools/`. The commit hook checks
  formatting; the pre-push gate runs `dart analyze` and `dart test` when the pushed files touch
  `tools/`; the Jenkins job `gerrit_check_tools` runs `dart test` only, when the patchset
  touches `tools/`, `analysis/`, `phone/packages/theme_schema/`, the root `Dockerfile` or
  `.dockerignore`, or its own Groovy file.
- What the gate does not prove:
  - `test/ensure_build_test.dart` is skipped unless `--run-skipped` is given, so a stale
    `version.dart` passes - run it after changing the version in `pubspec.yaml`;
  - `tool/docs_gate.dart` is run by no hook or job - run it after editing a page here;
  - a change only in `analysis/` does not trigger `tools-analyze` - run `dart analyze` here.
- Pushing, reworking a chain and reading Jenkins: the root [AGENTS.md](../AGENTS.md).

## Writing docs

- `docs/guides/` a procedure, `docs/reference/` what a reader looks up. Add a page to the
  Documentation list of [README.md](README.md): the docs gate wants every page reachable from
  a README.
- A path in backticks that starts with `lib/`, `bin/`, `test/`, `tool/` or `docs/` must exist;
  the docs gate checks it. Plain ASCII.
